# v1.3.3 release report — bypass ExtPay popup, tab-only

## What v1.3.2 got wrong

v1.3.2 wrapped `extpay.openLoginPage()` and `extpay.openPaymentPage()`
in `try / catch` with a tab fallback in the catch. That looked right but
**structurally cannot catch the error in question**:

- `chrome.windows.create(...)` returns a promise.
- The SDK's `open_popup()` (lib/extpay.js:1416-1448) **awaits** that
  promise — but `open_popup` is itself called as the *last expression*
  of `open_login_page`, and the SDK never `await`s the inner
  `windows.create` from the OUTER public method. The outer
  `openLoginPage()` resolves successfully BEFORE the inner promise
  rejects on bounds.
- The rejection then surfaces as an **unhandled promise rejection**
  at the global level, which our `await extpay.openLoginPage()` had
  no chance to intercept.

So v1.3.2's `try/catch` was theatrical — it never triggered, and the
fallback URL never ran.

## What v1.3.3 changes

Stop calling `extpay.openPaymentPage` / `extpay.openLoginPage` at all.
Build the exact same URLs the SDK builds, read the same `api_key` the
SDK stores, and open them via `chrome.tabs.create` — which has no
bounds math and no internal popup-window flow to fail.

`lib/extpay.js` is **untouched** (the SDK still drives polling,
`onPaid`, `getUser`, the content-script auto-trigger on `/paid`, etc.)

## Audit findings (the URLs and key we now build)

| Action | Storage source | URL we now `chrome.tabs.create` |
|---|---|---|
| Upgrade (with api_key) | `chrome.storage.local.extensionpay_api_key` | `https://extensionpay.com/extension/cleanfeed2342/choose-plan/pro?api_key=<KEY>` |
| Upgrade (no api_key yet) | — | `https://extensionpay.com/extension/cleanfeed2342?back=choose-plan` |
| Login (with api_key) | same | `https://extensionpay.com/extension/cleanfeed2342/reactivate?api_key=<KEY>&back=choose-plan&v2` |
| Login (no api_key yet) | — | `https://extensionpay.com/extension/cleanfeed2342/reactivate?back=choose-plan` |

Both URLs match what `open_payment_page("pro")` and `open_login_page`
internally build (verified against lib/extpay.js lines 1455, 1457,
1484). The `api_key` is the same one the SDK persists at the same
storage key, so when the user arrives on ExtPay's page their existing
license / cart / saved card is recognised exactly as before.
