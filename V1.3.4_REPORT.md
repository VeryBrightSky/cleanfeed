# v1.3.4 release report — force api_key generation before tab-open

## Why v1.3.3 still 404'd

v1.3.3 bypassed the SDK's bounds-error popup successfully by tab-opening
ExtPay's URL directly. But the URL was missing the `?api_key=...` query
param, and ExtensionPay's hosted backend rejects requests without it
with **404 API key required**.

We assumed the api_key already existed in storage by the time the user
clicked Upgrade. It did not. The SDK only ever creates a key inside
`open_payment_page` / `open_login_page` (lib/extpay.js:1452-1454,
1481-1483) — both of which v1.3.3 stopped calling. So the key was
never generated.

The spec proposed calling `extpay.getUser()` to force generation, but
auditing `fetch_user()` (lib/extpay.js:1353-1362) revealed it does NOT
create a key on miss — it just returns a stub `{paid:false}` object.
Neither does `startBackground()` (lines 1556-1568) or the module-level
init (lines 1294-1304). Only the two popup-opening methods do.

## Audit findings (storage path discovered)

| Question | Answer |
|---|---|
| Storage key name | **`extensionpay_api_key`** (flat string, not nested in `extensionpay_user`) |
| Storage area | SDK writes via `set()` helper which **tries `chrome.storage.sync` first**, falls back to `chrome.storage.local` only on sync failure (lib/extpay.js:1266-1273) |
| Generator | `create_key()` at lib/extpay.js:1307-1340 — POST `https://extensionpay.com/extension/<id>/api/new-key`, body `{}` or `{development: true}`, response is the raw api_key as a JSON string. SDK then `set({extensionpay_api_key: api_key})`. |
| Trigger sites in SDK | Only `open_payment_page` (line 1453) and `open_login_page` (line 1482). NOT `getUser` / `fetch_user`. |
| URL the SDK builds (payment, plan=pro) | `${EXTENSION_URL}/choose-plan/pro?api_key=<KEY>` |
| URL the SDK builds (login) | `${EXTENSION_URL}/reactivate?api_key=<KEY>&back=choose-plan&v2` |

## What v1.3.4 changes

`background.js` gains four small helpers (still no edit to `lib/extpay.js`):

- `_readExtpayApiKey()` — read the key from `chrome.storage.sync` first, then `chrome.storage.local`. Matches the SDK's read order so subsequent SDK calls see the same key we created.
- `_writeExtpayApiKey(apiKey)` — symmetric write (sync first, fallback to local).
- `_createExtpayApiKey()` — direct replica of SDK's `create_key()`: POSTs `/api/new-key`, parses the JSON string response, writes to storage. Dev-mode detection is inlined (`!('update_url' in chrome.runtime.getManifest())`) instead of `chrome.management.getSelf` since we don't carry the `management` permission.
- `_ensureExtpayApiKey()` — try-read; if missing, call `extpay.getUser()` (harmless, in case some future SDK release adds lazy creation there); re-read; if still missing, call `_createExtpayApiKey()`. Returns `""` only when both read AND create fail (offline, network-blocked).

Both message handlers (`cf:open-payment*` and `cf:open-login*`) now call `_ensureExtpayApiKey()` before building the URL, and respond `{ok:true, hasApiKey: !!apiKey}` so the popup-side caller can tell whether the new tab will land on a working page or the no-key fallback.

## How to verify locally

1. `chrome://extensions` → Load unpacked → pick `cleanfeed/`.
2. **Reset storage first** to simulate a fresh install: in the service
   worker DevTools console, run `chrome.storage.sync.clear(); chrome.storage.local.clear();`. Then reload the extension.
3. Open popup → click **Upgrade — $4.99**. New tab opens. The address bar should now show `extensionpay.com/extension/cleanfeed2342/choose-plan/pro?api_key=<long string>`. Page renders the Pro checkout, not "API key required".
4. Right-click the extension icon → service-worker console. You should see no errors. If `_createExtpayApiKey()` had to fetch, you may briefly see a network request to `/api/new-key`.
5. Click **I already paid**. New tab opens at `…/reactivate?api_key=<long string>&back=choose-plan&v2`. Page renders the magic-link login form, not 404.
